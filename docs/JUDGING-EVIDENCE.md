## Product choice and demonstration

Prioritize a worker-controlled record and a reviewer who can inspect it without trusting the application server. Keep the worker capture flow free of payment/wallet complexity where sponsorship is available. Do not add Intents payouts merely to increase a feature count: payments do not resolve the current evidence or adoption gaps.

Use the first platform/city where the builder can obtain consented worker and reviewer access. Until that is known, platform is an optional worker-supplied field, no platform integration is claimed, and no city or worker population is invented. Existing captured records are never relabelled to create a history under the new brand or an authenticated account.

The demo should show a clearly labelled synthetic record if real-data permission is unavailable. Show the exact disclosed notes, screenshot inclusion and location count before publication; unchecked records stay local. Download the pack, verify with the standalone CLI and change a disclosed amount to demonstrate rejection. The new cited review brief is deterministic and **unattested**, not a substitute for NEAR AI Cloud execution. Distinguish a local mock demonstration from an actual transaction on every screen and in narration.

## Originality: compare behavior, not slogans

[Worker Info Exchange](https://www.workerinfoexchange.org/) describes work on data access requests, investigations supporting challenges to automated management decisions, and worker data trusts. Appeal addresses a narrower engineering question: can a reviewer check selected worker-held records against prior commitments without receiving all private entries? This is a complementary use case, not evidence that Worker Info Exchange lacks any particular capability. Its existence also means worker data rights are not a new problem invented by this project.

The [New Jersey Future of Work Accelerator profile of Driver’s Seat](https://accelerator.fow.nj.gov/participants/drivers-seat-cooperative) describes shared driver data, earnings insights and planning/policy uses. Treat this as the accelerator's description, not a verification of the product's current availability or feature set. Appeal's current demonstration focuses on the integrity and selective disclosure of a particular evidence pack; it does not provide a driver-owned marketplace or city analytics service.

| Reviewer question | Ordinary local screenshot folder | Appeal component demonstrated locally |
|---|---|---|
| Can I detect later edits against a prior external commitment? | A folder alone provides no external commitment | NEAR verifier checks actual finalized receipts when a real deployment is supplied; current local demo uses a labelled mock ledger |
| Can I disclose selected structured records while proving membership in a larger commitment? | Folder organization alone supplies no membership proof | Salted Merkle proofs for selected records; hidden record contents stay unavailable |
| Can I verify without trusting the case server's summary? | Manual review is possible, but no shared deterministic computation is inherent | Shared summary recomputation and independent CLI; cited deterministic review brief |
| Does it prove truth, employment, automatic capture, completeness or a correct device clock? | No | No. Account authorization and commitment timestamps are narrower claims |

No claim of novelty follows merely from using a blockchain. Test whether the reviewer values these narrower checks and whether simpler signed exports would satisfy the same need. Keep that feedback even if it challenges the product thesis.

## Consented pilot protocol

Recruit only actual people the builder can reach. Do not contact organizations or send private records without explicit instructions. Begin with synthetic tasks; use real records only after explaining data handling and receiving consent. Store completed notes and quotes outside Git, for example under ignored `pilot-data/` with restricted local access.

Record the session date, anonymous participant reference, role, selected platform/city, device/browser, observed task and observer. Keep contact details and permission records separately. Consent choices must separately cover participation, any real evidence processing, feedback notes, public quotations and public screenshots/video. Participation does not imply permission to publish a quote or a record. Explain that hosted reviewer links currently have no expiry or revocation; keep real identifying data out of public demonstrations.

Worker tasks:

1. Record a synthetic trip and notice, decline location, attach a non-identifying screenshot and reload offline. Ask the participant to explain what is stored and what is public.
2. Export a backup and restore it on an empty browser profile. Observe errors or uncertainty; do not clear an existing journal to force a successful test.
3. Select one record while keeping another private. Ask what they expect to leave the device, then inspect the disclosure preview together. Verify the outgoing pack actually excludes the private record.
4. Ask about a real past review/dispute workflow without collecting unnecessary personal details. Record their words and any missing requirement; do not equate a hypothetical scenario with actual adoption.

Reviewer tasks:

1. Inspect the pack and cited brief. Identify what the commitment/account checks prove and what remains self-reported.
2. Locate an entry by its citation, inspect any disclosed screenshot, find the transaction/receipt reference and explain missing context.
3. Load an altered pack and observe rejection. Ask whether these checks change their assessment or simply add work.
4. Ask which existing process this could replace or complement, what they would require before using it, and why they might reject it. Do not ask them to certify legal admissibility from a demo.

For each task record outcome (`completed`, `assisted`, `failed`, `declined`), observed steps, actual start/end times if timing was consented, errors and exact feedback. Missing observations remain missing. Count distinct consented participants, completed tasks and actual reviewed packs from these records; exclude developers, automated tests and duplicate sessions from adoption claims. Any before/after timing comparison must use comparable tasks, state assistance and acknowledge order/learning effects. Do not present a small convenience sample as representative impact.

## Sustainability validation

Initial hypothesis: workers keep a free local journal; a union/legal-aid organization may sponsor verifications or a managed reviewer workflow. This is a hypothesis, not a chosen price or a partnership. Do not sell personal worker evidence or make consent a condition of receiving help.

Ask a real prospective budget holder what they use today, case volume they can substantiate, reviewer effort, procurement/privacy requirements, who approves a purchase, and what would prevent a pilot. Record the evidence category: problem confirmed, demo feedback, pilot interest, accepted quote, paid invoice or rejection. A compliment or an unsigned letter of interest is not revenue. Obtain separate permission before naming an organization publicly.

Measure actual host/storage/backup costs, successful and failed transaction fees, support/reviewer effort and any real TEE/model charge. Keep measurement window, currency, receipts/quotes and the method for allocating shared costs. Mainnet token conversion requires a dated actual price source; testnet tokens have no validated operating-price relationship. Include unpaid labor explicitly rather than silently pricing it at zero.

Run `npm run economics -- <private-local-cost-scenario.json>`. The input requires `currency`, `period`, `fixedCosts` and `variableCostsPerPack` item arrays, each with `label`, `amountMinor` (integer string) and `source`, plus `pricePerPackMinor`, `priceSource` and `priceBasis` (`proposed`, `accepted_quote` or `paid_invoice`). All amounts use the same currency's minor unit and the same pack definition. Zero costs must still have a source. No numerical default is supplied. The output computes contribution and break-even packs using exact integers; it cannot validate demand or price acceptance. Keep scenarios containing private quotes under ignored `validation-data/`.

## Gates that cannot be replaced with better copy

- A successful public testnet deployment and an independently verified worker-authorized transaction.
- A supported physical Android capture/recovery test; automatic notification capture remains separate.
- Actual supported TEE execution and verified attestation before claiming private AI attestation.
- Consented worker/reviewer observations before claiming usefulness or impact.
- Real buyer/cost evidence before claiming willingness to pay or sustainability.

Do not change the status of these gates until the evidence exists. Publication remains subject to the owner's current instruction to keep the code local; Git identity is configured, but no backdated commits or push are performed.
